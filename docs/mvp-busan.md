# 트렌디 MVP 명세 — 부산 단독

전국 범위를 접고 **부산광역시 하나만** 제대로 만드는 것으로 MVP를 축소한다.
SNS 크롤링(X·인스타그램)은 약관 리스크와 확보 불확실성이 커서 MVP에서 제외하고, **공공·상용 API 기반 대안 소스**만 사용한다.

## 1. MVP 범위

| 항목 | 내용 |
| --- | --- |
| 지역 | 부산광역시 16개 구·군 → 행정동 |
| 데이터 소스 | 공공 API + 검색 API (SNS 크롤링 없음) |
| 갱신 주기 | 1일 1회 배치 (실시간은 이후 단계) |
| 화면 | 부산 실루엣 워드클라우드 지도 1개 + 카테고리 토글 |
| 검증 목표 | "지도 위 키워드가 재미있게 읽히는가" |

## 2. UI 컨셉 — 부산 모양 워드클라우드

부산광역시 경계 실루엣 안을 키워드 텍스트가 채우는 형태. 글자 크기 = 점수, 글자 색 = 카테고리.

### 2.1 줌 레벨별 동작

| 레벨 | 줌 | 표시 단위 | 키워드 구성 |
| --- | --- | --- | --- |
| L1 | ~10 | 부산 전체 실루엣 | **카테고리별로 묶은 대표 키워드** 30~50개. 부산 전체를 대표하는 큰 키워드 위주 |
| L2 | 11~12 | 구·군 (16개) | 구·군별 3~5개 |
| L3 | 13~ | 행정동 / 역세권 | 동별 3~5개, 세부 장소·상권 단위 |

줌 전환 시 키워드는 사라졌다 나타나는 것이 아니라 **크기·투명도가 연속적으로 보간**되어야 탐색의 재미가 산다.

### 2.2 ⚠️ 해결해야 할 설계 충돌: 실루엣 채우기 vs 실제 좌표

참고 이미지 같은 일반적인 워드클라우드는 단어를 **실루엣에 예쁘게 채워 넣는 것**이 목적이라 단어 위치에 의미가 없다.
반면 트렌디는 **"그 키워드가 그 동네의 것"**이라는 게 서비스의 전부다. 둘은 그대로 양립하지 않는다.

**채택안: 실제 좌표 우선 + 폴백 키워드로 여백 채우기**

1. 모든 키워드는 소속 행정동의 중심점(centroid)에 배치한다 — 위치는 항상 진짜다.
2. 라벨끼리 겹치면 점수가 높은 쪽이 이기고, 낮은 쪽은 **부산 경계 폴리곤 내부에서만** 밀려난다 (point-in-polygon 제약).
3. 트렌드 데이터가 없어 비는 구역은 **지명·역명 키워드로 채운다** (3.2절).

→ 결과적으로 부산 실루엣이 자연스럽게 채워지면서도, 모든 글자가 실제 위치를 지킨다.
**"트렌드가 없으면 지명이나 역명을 쓴다"는 규칙이 곧 실루엣의 여백을 메우는 장치**이기도 하다.

## 3. 키워드 정책

### 3.0 키워드 계층 — 상호(가게 이름)까지 내려간다

지도를 실제로 채우는 것은 상권·명소 이름이 아니라 **개별 가게 이름**이다.
`전포카페거리` 하나보다 그 거리의 가게 이름 열 개가 화면을 채우고, 트렌드도 그 단위에서 움직인다.

| 계층 | 예 | 좌표 출처 |
| --- | --- | --- |
| 상권·거리 | 전포카페거리, 해리단길 | 지명 사전 |
| 명소·랜드마크 | 오시리아, 해동용궁사 | TourAPI |
| **상호 (가게)** | 개별 카페·식당·상점 | **카카오 로컬 API / 네이버 지역검색** |

**상호 계층에는 가게마다 자기 좌표가 반드시 있어야 한다.** 행정동 대표점을 물려받으면
같은 동의 가게가 전부 한 점에 쌓여, 이름을 아무리 많이 넣어도 라벨이 겹쳐 사라진다
(7절 실측 참고).

상호를 다룰 때의 제약:

- **폐업·상호 변경이 잦다.** 수집 시점을 함께 저장하고, 일정 기간 갱신되지 않은 상호는 내린다.
- **광고·어뷰징 유인이 생긴다.** 특정 가게가 지도에 뜨는 것 자체가 이익이므로, 언급량 조작에
  견디는 스코어링(단일 출처 가중치 상한, 신규 계정 언급 할인)이 필요하다.
- **근거를 남긴다.** 키워드를 클릭하면 그 가게가 왜 떴는지(언급 수, 출처 링크)를 보여준다.
  근거 없이 상호만 띄우면 광고와 구분되지 않는다.

### 3.1 키워드는 핫플레이스·맛집일 필요가 없다

그 지역을 설명하는 것이면 무엇이든 키워드가 된다 — 장소, 음식, 행사, 풍경, 분위기, 지역 특성.
카테고리(= 색상) 초안:

| 카테고리 | 예시 |
| --- | --- |
| 맛집·먹거리 | 돼지국밥, 밀면, 씨앗호떡 |
| 카페·디저트 | 전포카페거리, 로스터리 |
| 뷰·자연 | 해운대, 이기대, 야경 |
| 문화·행사 | 영화제, 불꽃축제, 비엔날레 |
| 생활·지역 | 시장, 재개발, 대학가 |

### 3.2 폴백 규칙 (콜드 스타트 대응)

한 구역에서 점수가 임계값을 넘는 키워드를 확보하지 못하면, 아래 순서로 대체한다.

1. **랜드마크·대형 POI** — TourAPI 기반 (예: `해동용궁사`, `오시리아`, `아난티`)
2. **가까운 역명** — 도시철도·동해선 역명 (예: `물만골역`, `일광역`)
3. **행정동명** — (예: `구포`, `다대포`)
4. 그래도 없으면 상위 구·군 키워드를 축소 표시

랜드마크를 역명·지명보다 앞에 두는 이유는, 저밀도 구역일수록 행정동명이 사람들이 실제로
부르는 이름과 멀어지기 때문이다(예: 기장군 `일광읍`보다 `오시리아`가 읽힌다).

**밀도 적응은 과밀 쪽만 다룬다.** 7절 실측대로 구역별 라벨 밀도 편차가 100배 넘게 나지만,
**저밀도 구역의 공백은 메우지 않기로 했다**(6.1절). 고밀도 구역에서 폴백을 1순위에서 끊는
규칙만 유지하고, 저밀도 구역을 채우려고 폴백을 더 깊이 내려가지 않는다.

폴백 키워드는 트렌드 키워드와 **시각적으로 구분**한다 (낮은 채도 / 작은 크기). 빈 곳을 메우되, 진짜 트렌드인 척하지 않는 게 중요하다.

## 4. 데이터 소스 (대안 소스)

SNS 대신 아래를 조합한다. **좌표를 함께 주는 소스(TourAPI, 카카오 로컬)가 지오코딩 비용을 크게 줄여주므로 우선순위가 높다.**

| 소스 | 얻는 것 | 좌표 | 상태 |
| --- | --- | --- | --- |
| [한국관광공사 TourAPI](https://api.visitkorea.or.kr/) (`areaBasedList` / `locationBasedList`) | 관광지·음식점·숙박·행사, `mapX`/`mapY` 좌표 | ✅ 제공 | 존재 확인 |
| [부산광역시 부산축제정보 서비스](https://www.data.go.kr/data/15063500/openapi.do) | 지역 축제·행사 일정 | 부분 | 존재 확인 |
| [부산 Big-데이터웨이브](https://data.busan.go.kr/bdip/) | 상권, 관광실태조사, 부산 특화 데이터 | 데이터셋별 상이 | 존재 확인 |
| 네이버 검색 API (지역/블로그) | `"서면 + 키워드"` 검색 결과 수 → **언급량 근사** | ❌ | 쿼터·약관 확인 필요 |
| 네이버 데이터랩 검색어트렌드 API | 키워드 시계열 → **burst(급상승) 산출** | ❌ | 아래 주의 참고 |
| 카카오 로컬 API | POI·카테고리 조회, 좌표 정규화 | ✅ | 쿼터 확인 필요 |
| 부산교통공사 역별 승하차 (공공데이터포털) | 역세권 가중치, **역명 폴백 사전** | 역 좌표 별도 | 확인 필요 |
| SGIS / 국가공간정보포털 행정동 경계 | 부산 실루엣·행정동 폴리곤·centroid | ✅ | 확인 필요 |

### 4.1 네이버 데이터랩 검색어트렌드 API의 역할과 한계

데이터랩은 **후보 키워드의 급상승(burst)을 재는 계측기**로는 쓸 수 있지만,
후보를 발굴하는 용도로는 쓸 수 없다. 제약이 세 겹이다.

1. **지역 파라미터가 없다.** 지원 조건은 기간·기기·성별·연령대뿐이다. 지역 신호는 API가
   주는 게 아니라 **검색어 문자열에 지명을 넣어(`"광안리 카페"`) 우리가 만들어야** 한다.
   지명·상호 사전이 파이프라인의 핵심 자산이 되는 이유다.
2. **절대량이 아니라 상대값이다.** 각 응답은 그 호출 안에서 최대값을 100으로 정규화한다.
   따라서 **서로 다른 호출의 값을 그대로 비교할 수 없다.** 매 호출에 고정 기준어(예: `부산`)를
   한 그룹으로 넣어 스케일을 맞춰야 지역·키워드 간 비교가 성립한다.
3. **호출량이 제한된다.** 1일 1,000회, 한 호출에 검색어 그룹 5개.
   기준어 한 그룹을 고정으로 쓰면 실질 4개/호출이다.

산술적으로: 키워드 165개면 42회, 2,000개면 500회. **일일 한도 안에는 들어오지만
전수 조사에는 여유가 없다.** 그래서 순서가 이렇게 된다.

```
후보 발굴  카카오 로컬 · TourAPI · 네이버 지역/블로그 검색  (수천 건)
   ↓ 언급량으로 컷
상위 후보  구·군별 상위 N개                                  (수백 건)
   ↓ 데이터랩으로 시계열만 측정
burst 확정 기준어를 낀 4개씩 배치 호출                         (수십~수백 회)
```

데이터랩을 파이프라인 앞단에 두면 한도가 먼저 터진다. **뒷단의 계측기로 쓴다.**

## 5. 구현 순서

1. **지오메트리 확보** — 부산 행정동 경계 GeoJSON → 구·군/전체 단위로 병합(union)해 3단계 실루엣 생성, centroid 산출
2. **지명·역명 사전 구축** — 행정동명 + 도시철도 역명 + 주요 상권명. 폴백과 검색어 조합에 모두 쓰인다
3. **수집 스크립트** — TourAPI·축제 API로 기반 POI/행사 확보 → 사전의 지명과 조합해 검색 API로 언급량·burst 측정
4. **스코어링** — `tfidf × burst × recency` ([기술 설계 메모](technical-plan.md) 2절), 결과를 정적 GeoJSON으로 출력
5. **렌더링 프로토타입** — MapLibre GL JS `symbol` 레이어 + 부산 실루엣 마스크, 줌 레벨별 라벨 보간. **백엔드 없이 정적 파일로 먼저 검증**
6. 검증 통과 후에야 배치 워커·API 서버를 만든다

## 6. 열린 질문

- L1에서 "카테고리로 묶은 큰 키워드"의 위치는 어디인가? 해당 카테고리 점수의 가중 중심점(weighted centroid)을 제안한다
- 카테고리 5종이 색으로 구분 가능한 최대치인가? 색맹 대응 팔레트 필요
- 폴백 키워드 비중 상한 — 화면의 절반 이상이 지명이면 "트렌드 맵"이 아니게 된다

## 6.1 결정 — 저밀도 구역의 공백은 수용한다

기장군·강서구처럼 트렌드도 가게도 드문 구역은 **비워 둔다.** 억지로 채우지 않는다.

근거: 그런 구역에 라벨을 채우려면 결국 (a) 트렌드가 아닌 지명·행정 정보를 트렌드인 척
배치하거나, (b) 좌표를 근사해 실제 위치를 흐리게 된다. 둘 다 "이 키워드가 이 동네의 것"이라는
서비스의 전제를 깎아먹는다. **한산한 동네가 한산하게 보이는 것은 오류가 아니라 정보다.**

이 결정이 범위에 미치는 영향:

- 저밀도 구역용 랜드마크 확보(오시리아·가덕도 등)는 **더 이상 선결 과제가 아니다.**
  따라서 **TourAPI 연동의 우선순위가 내려간다.**
- 남는 과제는 반대쪽 하나다 — **원도심 과밀.** 여기는 라벨이 실제로 서로를 밀어내 정보가 사라진다.
- 폴백 라벨(구·군·행정동 이름)은 그대로 둔다. 이건 실제 위치의 실제 이름이라 위 문제가 없다.

## 7. 커버리지 실측 (2026-07-01 경계 기준)

1~2단계 산출물로 **폴백 라벨만 배치했을 때** 부산 실루엣이 얼마나 채워지는지 측정했다.
미리보기: [`data/busan/preview-fallback-labels.svg`](../data/busan/preview-fallback-labels.svg)

- 행정동 라벨 206개 중 **145개 배치 / 77개는 겹쳐서 탈락** (구·군 라벨 포함 222개 기준)
- 실루엣 내부 0.5km 격자 3,135개 기준, 가장 가까운 행정동 라벨까지 거리
  - 중앙값 **1.24km**, 90퍼센타일 **3.27km**, 최대 **6.96km**
  - 2km 초과 공백이 면적의 **31.8%**, 3km 초과가 **13.8%**

| 기장군 | 220.0 km² | 5 | **0.023** |
| 강서구 | 188.4 km² | 9 | **0.048** |
| … | | | |
| 동구 | 9.5 km² | 12 | 1.268 |

- **저밀도(공백):** 기장군·강서구 두 곳이 부산 면적의 **약 35%**인데 행정동 라벨은 14개뿐이다.
  중구 대비 밀도가 100분의 1 수준이라, 행정동명만으로는 이 두 구역의 공백이 메워지지 않는다.
  → 3.2절의 랜드마크·역명 폴백이 **이 두 구역에서 특히 중요**하다. 우선 확보 대상:
  기장군(해동용궁사·오시리아·일광·정관), 강서구(명지·에코델타·가덕도·경전철 역세권).
- **고밀도(과밀):** 원도심(중구·동구·서구)은 라벨이 서로 밀어내 3분의 1이 탈락한다.
  → 줌 L3에서 동 단위보다 더 잘게 쪼개거나, 줌 구간을 하나 더 두는 편이 낫다.

### 다음 단계에 넘길 결론

> 아래 1번은 6.1절 결정으로 **철회되었다.** 저밀도 구역은 채우지 않는다.
> ~~폴백 사전에 랜드마크 POI 계층을 반드시 추가한다~~

1. 남는 과제는 **원도심 과밀**이다. 고밀도 구역에서 점수 상위만 남기고,
   줌 L3를 원도심에서 한 단계 더 세분화할지 검토한다.
2. 가게별 실제 좌표(카카오 로컬 API)는 여전히 필요하다. 이건 공백 때문이 아니라,
   좌표 없이는 같은 동의 가게들이 한 점에 쌓여 **어느 구역에서든** 라벨이 사라지기 때문이다.

## 8. 상호 계층 반영 후 실측 (프로토타입)

샘플 키워드를 77개 → 165개로 늘리고 실제 상호 16건을 섞어 다시 측정했다.

- **이름을 늘리는 것만으로는 채워지지 않았다.** 같은 행정동에 묶인 키워드가 모두 동 대표점
  한 점을 물려받아, 기장군은 라벨이 2개에서 4개로 느는 데 그쳤다. 겹친 나머지는 전부 탈락했다.
- 좌표를 동 안에서 분산시키자 기장군 라벨이 7개로 늘었다. 다만 기장읍처럼 100km²가 넘는
  폴리곤에서는 분산 반경을 제한하지 않으면 라벨이 실제 위치에서 수 km 벗어난다
  (아난티 코브가 오시리아가 아닌 내륙에 찍혔다). **반경 상한 1.4km**를 두어 해결했다.
- 프로토타입의 분산 좌표는 `approx` 플래그로 표시하고 툴팁에 "동 내 근사 위치"로 밝힌다.
  실제 POI 좌표가 들어오면 전부 대체된다.

**결론: 상호 계층의 값어치는 이름이 아니라 좌표에 있다.** 가게별 좌표 없이 이름만 늘리면
같은 자리에서 서로를 밀어낼 뿐이다. 카카오 로컬 API 연동이 이 계층의 선결 조건이다.

## 9. 범위 확정 후 남은 선결 과제

6.1절 결정으로 저밀도 구역 대응이 빠지면서, 남은 병목은 하나다.

| 과제 | 상태 |
| --- | --- |
| **카카오 로컬 API — 가게별 좌표** | **선결.** 없으면 같은 동 키워드가 한 점에 쌓인다 |
| 네이버 검색 API — 언급량 근사 | 필요. 후보 발굴 단계 |
| 네이버 데이터랩 — burst 계측 | 필요. 파이프라인 뒷단 (4.1절) |
| TourAPI — 랜드마크 | **우선순위 하향.** 저밀도 구역을 채우지 않기로 하면서 급하지 않다 |
| 원도심 과밀 해소 | 설계 과제. 데이터 없이도 착수 가능 |
